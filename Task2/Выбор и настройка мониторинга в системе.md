# Выбор и настройка мониторинга в системе

## Мотивация

- Сейчас о проблемах мы узнаём из жалоб клиентов и партнёров. Яндекс Метрика видит только сайт, а заказы через API и работа CRM, MES и RabbitMQ остаются невидимыми.
- Мониторинг покажет, на каком шаге застревают заказы (расчёт стоимости, очередь, производство), а алерты сообщат о проблеме раньше, чем клиент пожалуется.
- Что получит бизнес: меньше просроченных заказов и потерянных контрактов. Решения об улучшениях принимаются по цифрам, а их результат виден на графиках.
- Затраты небольшие: Prometheus и Grafana бесплатны, внедрение займёт несколько недель работы DevOps-инженера и бэкенд-разработчиков.

## Выбор подхода к мониторингу

| Часть системы | Подход | Почему |
|---|---|---|
| API онлайн-магазина, CRM API, MES API (включая API для партнёров) | RED | Это сервисы, которые обрабатывают запросы. Важно то, что чувствует пользователь: сколько запросов, сколько ошибок, как долго ждать ответа. |
| Инфраструктура: инстансы EC2, БД, RabbitMQ, S3 | USE | Это ресурсы. Важно, насколько они загружены и не стали ли узким местом. |
| Заказы | Бизнес-метрики | Количество заказов и время в каждом статусе напрямую показывают задержки, на которые жалуются клиенты. |

Инструменты: Prometheus собирает метрики, Grafana показывает дашборды и отправляет алерты.

## Метрики

| Метрика | Где | Зачем | Ярлыки |
|---|---|---|---|
| Количество запросов (RPS) | API магазина, CRM, MES | Видеть нагрузку и её рост, отдельно от B2C и от партнёров. | `service`, `endpoint`, `client_type` (B2C / партнёр), `partner_id` для MES API |
| Количество ответов HTTP 2xx, 4xx, 5xx | API магазина, CRM, MES | Доля ошибок: 5xx — сбой у нас, 4xx от партнёров — проблемы с интеграцией. | `service`, `endpoint`, `status_code`, `partner_id` для MES API |
| Время ответа (latency, p95/p99) | API магазина, CRM, MES | Найти медленные запросы, в первую очередь дашборд MES. | `service`, `endpoint` |
| Загрузка CPU и памяти, % | Инстансы приложений и БД | Единственные инстансы — узкое место; метрика подскажет, когда масштабироваться. | `instance`, `service` |
| Количество подключений к БД | БД магазина, БД MES | Нехватка подключений замедляет все запросы к API. | `db` |
| Размер БД и хранилища S3 | БД, S3 | 3D-модели занимают много места, заказов всё больше: нужно вовремя увеличить объём. | `db` / `bucket` |
| Количество сообщений в очереди | RabbitMQ | Растущая очередь значит, что получатель не успевает и заказы ждут. | `queue` |
| Количество сообщений в dead letter exchange | RabbitMQ | Каждое такое сообщение — потерянный заказ, алерт при значении больше нуля. | `queue` |
| Количество заказов в каждом статусе (новая) | MES, CRM | Видно, в каком статусе копятся заказы. | `status`, `source` (B2C / партнёр) |
| Время нахождения заказа в статусе (новая) | MES, CRM | Главная жалоба — заказы «зависают». Алерт, если заказ находится в статусе дольше нормы. | `status`, `source` |
| Длительность расчёта стоимости и число расчётов в ожидании (новая) | MES | Расчёт — главное узкое место, метрика покажет, хватает ли мощности. | `source`, `result` (успех / ошибка) |

В ярлыки не добавляем `user_id` и `order_id`: на каждого пользователя и каждый заказ появится отдельный график, и дашборд станет нечитаемым. Конкретный заказ удобнее искать в логах или в CRM.
